## 职责和修改范围

| 工作 | 实验端 A | 研发端 B |
|---|---|---|
| 负载启动、集群健康核验、采集 | 唯一执行方 | 查看摘要，提出采样需求 |
| 原始数据质检和封存 | 执行、登记哈希和可用性 | 复核特征、分布和误差 |
| 模型架构、损失、校准设计 | 评估部署约束 | 主责，交付代码和消融配置 |
| 远端 GPU 训练 | 唯一提交方，登记任务 | 提交可复现训练请求，分析结果 |
| CPU 导出和在线验证 | 执行、报告延迟及因果检查 | 修复候选模型兼容性 |
| 状态与数据清单 | 维护 STATUS 和数据集条目 | 维护候选说明和分析报告 |
| 正式测试 | 冻结模型后执行 | 不接触正式标签来调参 |

双方都能提出问题和修改代码；表中“唯一”是为了防止两个控制端重叠运行负载或争抢GPU。角色变更先由用户确认，再更新 `.local/ROLE.md` 和状态交接。

## 第一次交接

双方克隆仓库，各自建立本地角色文件。A 的原有 `F:\sessions\26.9.8_测试大纲\idfs_forecast_lab` 目前仍是现场工作目录；本仓库是整理后的协作副本。不要同时从两个目录启动批次。A 先在协作副本验证修改，再有选择地同步到现场目录，并记录实际执行的提交；不得覆盖原始证据。

B 先读 STATUS、DATA_CONTRACT 和已提交 reports。背景数据与冒烟可用于推理回放和排查，但不是正常五类负载训练集。B 需要数据时由 A 通过交接脚本生成包；数据包不随 `git clone` 自动出现，下载位置由 A 在数据条目中填写。

## 一次候选实验如何流转

1. B 建 `model/<简短主题>` 分支，编写设计说明，列出理论假设、基线、预期失败场景、消融项和评价指标。
2. B 提交候选代码和配置；用训练请求 issue 模板填写数据集ID、训练/验证轮、seed、epoch预算、依赖和预期输出。代码用提交SHA标识，不以“最新文件”交接。
3. A 拉取候选，确认无数据泄漏、依赖和输出接口兼容，再登记唯一 job_id。A 在提交时复核空闲GPU、磁盘和线程边界，按请求执行训练。
4. A 返回训练日志、模型哈希、逐窗口预测、分节点/分负载指标、导出对拍和CPU延迟；小摘要提交仓库，大包通过数据清单交接。issue记录状态：requested → accepted → running → completed/failed。
5. B 分析结果后继续迭代。开发验证集可用于选择，但需记录重复调参次数；最终另采独立测试轮。任何“达标”必须指明对象、公式和数据划分。

## 更新与冲突处理

每次开工先 `git status`，有本地修改先提交到自己的分支，再 `git fetch origin`。新工作从 `origin/main` 建分支：

```powershell
git fetch origin
git switch -c model/calibration-v1 origin/main
# 修改代码、跑测试，然后仅添加本次文件
git add <文件>
git commit -m "Describe the concrete change"
git push -u origin model/calibration-v1
```

A使用 `experiment/<主题>`，B使用 `model/<主题>`。在GitHub建PR，写清改动、数据版本、检查和风险。合并后另一端更新main；不要强推，不用文件同步软件合并 `.git`，不将旧目录整包覆盖新提交。没有启用分支保护；两端仍需按这个约定执行。

数据/任务登记冲突由A核对现场状态后解决；模型实现冲突由B整理后交A复测。合并改变特征顺序、拓扑、归一化、目标或协议时必须升级schema或协议版本，不允许只换权重继续用旧哈希。
