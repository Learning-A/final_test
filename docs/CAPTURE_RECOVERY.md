# 开发采集队列与故障恢复

`idfs_lab.capture_queue` 在每次调用中最多执行一个660秒采集尝试，队列跨调用持久保存，适合实验端心跳使用。默认不连接现场，只有 `--execute` 才执行。它不会自动修复OSS、重启进程或改变集群配置。

## 执行方式

仅由A执行。先使用默认计划模式，并明确提供私有现场配置：

```powershell
cd idfs_forecast_lab
python -m idfs_lab.capture_queue --out .local/batches/dev_20261122_v2 --site <私有site配置> --lock <A共用锁文件的绝对路径>
```

执行时增加 `--execute`；之后心跳用完全相同的命令重复调用。`--protocol`、`--workloads` 可指定配置；进入现场前必须审核配置内容与现有数据的准备状态。

20轮按五类交错采3轮训练，最后采独立验证。每次只推进最早未采集轮，成功的轮不会重跑。运行结果 `captured_pending_qa` 只代表采集和预处理结束，不能等同训练数据认证或准确率达标。

## 状态与恢复规则

| 状态 | 含义和下一步 |
|---|---|
| plan_only | 未执行、不连接、不创建队列 |
| waiting_environment | 健康/96 OSS/空闲进程检查未通过；不消费采集尝试次数 |
| running | 已登记当前尝试，正在调用现有采集器 |
| cooldown | 等待下一次检查时间，默认退避300秒 |
| between_rounds | 当前轮完成采集预处理，下一次调用推进下一轮 |
| captured_pending_qa | 全部轮采完；另做质量核验和数据清单登记 |
| retry_limit | 同一轮已使用3个尝试；保留证据，需分析后再调整预算 |

环境检查默认连续两次、间隔2秒；这只是启动门槛，不代表长时间健康保证。运行中每30秒检查，采样结束后再查。网络查询失败按健康未知处理，本次继续收集自然结束证据并排除正常训练，下一次检查恢复后重试。

`queue.json` 记录计划哈希、每轮状态和独立尝试目录。进程意外结束遗留的running尝试，下次标记interrupted并保留；必须重新核验远端空闲，才能另建attempt目录。不能凭本地PID消失就假定远端负载也结束。默认查询发现Java、Vdbench或相关采集/准备进程会等待，不给其他工作发信号。

锁使用操作系统文件锁，进程退出会释放。A所有调度入口须共用同一个绝对锁路径；旧 `collect_workloads` 直接入口没有该锁，不可并用。锁不提供跨电脑排他，B禁止启动现场负载。代码不会清理或覆盖旧attempt，也不会把旧故障轮转成正常数据。

## Baleen 配置目录

Baleen 的现场启动脚本默认使用 `config-idfs-workloads`，该目录缺少此负载的清单。显式指定 `/home/hust/idfs-workloads-fb83711/config` 后，只读 `verify` 返回 `ready`；文件大小和已分配空间符合预期，布局元数据未能独立核验。采集控制器对 Baleen 的 `verify` 和 `run` 使用相同目录，并检查它对应已登记的清单及哈希。其他负载继续使用脚本默认目录。

配置变更会改变队列配置哈希。原批次停在 `retry_limit`，三次失败证据及两轮已采数据均保留。恢复前先核验健康和并发任务，并为待采轮制定独立计划；不要编辑旧队列哈希或重复已采轮。
